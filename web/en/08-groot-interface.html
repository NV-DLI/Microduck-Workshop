5.2 Imitation learning: shoot autonomously with GR00T#

Connect imitation learning to Microduck’s skills. Training and inference are complete; no commands are needed.

Section 5.2 · Estimated learning time: 30 minutes

Task and demonstration#

Demonstrations use this fixed instruction:

Walk to the football, kick it into the goal with the right foot, and recover to standing.

8-D requests, hierarchical execution#

  • Movement, 3 values: forward, sideways and turning, limited to ±0.35, ±0.20 and ±0.80. These are policy commands, not measured rates.

  • Gaze, 4 values: neck pitch, head pitch, yaw and roll in radians, with position and rate limits.

  • Kick, 1 value: 0–1. Above 0.5, check stillness and head return before the roughly four-second kick/recovery skill. This is not a success probability.

The walking Actor converts requests and body feedback into joint targets, without an explicit IK or inverse-dynamics solver (see Section 2.2). This recording's kick/recovery combines reference policies, a trained residual correction and recovery logic; Section 4.3 uses official policies only.

Small skills handle balance every 20 ms while GR00T server inference takes about 0.33 seconds. The tradeoff is that high-level requests remain limited by available skills.

Model inputs#

Inputs are four 270 × 480 RGB frames (current and about 1.9, 3.8 and 5.8 seconds earlier), task text and a 127-dimensional state: joints and IMU, previous actions and requests, kick progress and historical state summaries.

Train the action head from successful episodes#

The onboard teacher demonstrates complete approach, alignment, kick and recovery. Split by whole episode. Align observations and requests every 80 ms with 16 future action labels; history must come from the past, and padded labels need validity masks.

This is behavior cloning (BC), a form of imitation learning: learn teacher actions without updating GR00T from goal rewards. The flow-matching head learns to recover demonstrated sequences from noisy actions.

Include deviations and corrections; repeated successes may not teach recovery from the model’s mistakes.

Control cycles and execution length#

Predict \(\htmlData{sym=H}{H}\) = 16 steps, execute the first \(\htmlData{sym=K}{K}\) = 4, then predict again from the latest observation. High-level requests run at \(\htmlData{sym=f_action}{f_{\mathrm{action}}}\) = 12.5 Hz, or 80 ms each; low-level control updates every 20 ms at 50 Hz.

Simulation time covered by a request prefix
\[\htmlData{sym=T_exec}{T_{\mathrm{execute}}} = \htmlData{sym=K}{K} / \htmlData{sym=f_action}{f_{\mathrm{action}}}\]
Variable meanings
\(T_{\mathrm{execute}}\)
Simulation time covered by one executed segment; 4 ÷ 12.5 Hz = 0.32 s here, excluding inference and communication time.
\(K\)
Request steps actually executed after each prediction; 4 here.
\(f_{\mathrm{action}}\)
Rate at which high-level requests are recorded and executed; 12.5 Hz here.

Four steps cover 320 ms of simulation time. The current synchronous implementation waits for inference before execution. Simulation pauses during this wait; host compute time is outside those 320 ms.

Control cycle

Onboard policy: RGB and ToF use nominal 15 Hz captures, followed by YOLO inference and localization. Every 20 ms, feedback control uses the latest perception and fresh body feedback to generate a motion request; the low-level Actor then generates joint targets.

GR00T: assemble an observation and wait synchronously for inference (about 300 ms on the DGX Spark server). Predict 16 requests and execute the first 4, each held for 80 ms; the Actor updates every 20 ms during execution. Observe and predict again after 320 ms. Cached requests also involve synchronous waits.

Rates are simulation settings, not measured runtime speed. Simulation pauses during computation; host inference time and simulation time use separate clocks and are not added.

Execution cannot exceed prediction length. Changing it preserves RGB capture, 80 ms observation/request updates and 20 ms low-level updates.

The execution horizon can be longer: eight steps cover 0.64 seconds, sixteen cover 1.28 seconds. Four steps are retained from an earlier small development comparison with limited data and training budget, where they yielded more successes. The current model has not repeated that comparison; four is neither a general recommendation nor an established optimum. Longer execution reduces inference waits but delays corrections. Extending the prediction horizon also requires model and label changes plus validation.

RTC extention: asynchronously predict the next chunk during execution, constraining the prefix that is too late to change. This recording does not use RTC. Buffering, timeouts and kick triggers still need handling; see GR00T deployment and LeRobot RTC.

Real-robot deployment#

Run the roughly 3B-parameter GR00T model on a GPU workstation, receiving images and state from the robot while small local skills control the body. Cloud inference adds network delay. Encoding, transfer and compute affect response time; disconnection or timeout should trigger a controlled stop.
