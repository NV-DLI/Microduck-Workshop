3.1 Reinforcement learning and PPO#

How reinforcement learning learns to walk from trial and error, why PPO limits each policy update, and where these formulas live in the Isaac Lab training code. This section covers the principles; Section 3.2 starts a training and tests a trained policy.

Section 3.1 · Theory · Estimated learning time: 30 minutes

The task: walk steadily on velocity commands#

Sections 2.1 and 2.2 only ran the official, fixed policy. Now the question changes: how can a randomly initialized policy learn to walk through repeated trials in simulation? This section connects the learning objective, rewards, advantage estimation and the PPO update to the actual Isaac Lab and RSL-RL code; Section 3.2 then starts training and tests the course’s pretrained policy.

We want the robot to coordinate its 14 joints when it receives forward, sideways and turning commands: keep balance while stepping, avoid slipping on the support foot, and move smoothly. Hand-writing a periodic trajectory for every joint hardly adapts to different speeds, forces and initial states at once.

Reinforcement learning learns control by “try an action → get feedback → adjust the policy” and needs no examples of “which joint angles for which state”: Newton produces the state transitions and the Isaac Lab reward manager describes the desired behavior.

Learning objective: increase long-term discounted return
\[\htmlData{sym=J}{J(\htmlData{sym=theta}{\theta})}=\htmlData{sym=E_traj}{\mathbb E_{\htmlData{sym=tau}{\tau}\sim\htmlData{sym=pi_theta}{\pi_\theta}}}\!\left[\sum_{\htmlData{sym=t_idx}{t}=0}^{\htmlData{sym=T_horizon}{T}-1}\htmlData{sym=gamma}{\gamma}^{\htmlData{sym=t_idx}{t}} \htmlData{sym=r_t}{r_t}\right]\]
Variable meanings
\(J(\theta)\)
Learning objective: the expected discounted return when sampling with the current policy; training adjusts the policy parameters to increase it.
\(\theta\)
Parameters (weights) of the policy network, updated during training.
\(\mathbb E_{\tau\sim\pi_\theta}\)
Expectation: an average over many trajectories sampled with the current policy.
\(\tau\)
One interaction trajectory: the observations, actions and rewards of an episode in order.
\(\pi_\theta\)
Policy: the neural network, set by its parameters, that maps an observation to a probability distribution over actions.
\(t\)
Index of a control step.
\(T\)
Number of control steps counted in the return of this trajectory; a different quantity from the steps sampled per iteration below.
\(\gamma\)

\(r_t\)
Immediate reward of the current control step: the weighted sum of all reward terms.

\(\htmlData{sym=theta}{\theta}\) are the policy parameters, \(\htmlData{sym=tau}{\tau}\) an interaction trajectory, \(\htmlData{sym=r_t}{r_t}\) the immediate reward and \(\htmlData{sym=gamma}{\gamma}\) the discount factor. Optimizing long-term return means that whether an action is good depends on whether the robot stays upright afterwards, not only on the reward of the current frame.

During training the policy network chooses actions from the 61-dimensional deployable observation; the value network may also read extra simulation information to estimate return. Only the policy network, which reads those 61 values, is exported; the extra simulation information the value network uses (for example base linear velocity and foot contact forces) is used only during training.

Turn “walking well” into rewards#

Rewarding only velocity tracking can produce unstable motion; rewarding only upright posture can teach the robot to stand still. The task therefore combines velocity tracking, posture, foot motion and action changes. Below is one actual reward term and how terms are combined; the complete list and weights are in the env.yaml saved with each training run.

Linear-velocity tracking reward
\[\htmlData{sym=r_v}{r_t^{v}}=\htmlData{sym=exp}{\exp}\!\left(-\frac{\|\htmlData{sym=v_cmd}{\mathbf v_{xy}^{\mathrm{cmd}}}-\htmlData{sym=v_xy}{\mathbf v_{xy}}\|_2^2+\htmlData{sym=v_z}{v_z}^2}{\htmlData{sym=sigma_v}{\sigma_v}^2}\right),\qquad \htmlData{sym=r_t}{r_t}=\htmlData{sym=dt}{\Delta t}\sum_{\htmlData{sym=i}{i}}\htmlData{sym=w_i}{w_i}\htmlData{sym=r_it}{r_{i,t}}\]
Variable meanings
\(r_t^{v}\)
Linear-velocity tracking reward of the current control step, between 0 and 1.
\(\exp\)
Exponential function: 1 when the error is 0, approaching 0 as the error grows.
\(\mathbf v_{xy}^{\mathrm{cmd}}\)
Horizontal part of the velocity command (m/s).
\(\mathbf v_{xy}\)
Actual horizontal body velocity (m/s).
\(v_z\)
Vertical body velocity (m/s); its square is part of the error, which discourages bouncing.
\(\sigma_v\)
Tolerance scale for the velocity error, `std` in the code.
\(r_t\)
Immediate reward of the current control step: the weighted sum of all reward terms.
\(\Delta t\)
Duration of one control step: reward terms are accumulated per time step.
\(i\)
Index of a reward term.
\(w_i\)
Weight of one reward term.
\(r_{i,t}\)
Value of one reward term at the current control step.

The smaller the velocity error, the closer this exponential reward is to 1; vertical velocity is penalized too, so bouncing does not count as ideal translation. \(\htmlData{sym=sigma_v}{\sigma_v}\) sets the tolerance. The reward manager multiplies each term by its weight and accumulates over the control time step \(\htmlData{sym=dt}{\Delta t}\); when comparing reward curves, check that weights and time step match.

Python · core excerptFull source ↗

1Compute the velocity error

For each environment, xy_error is the squared difference between horizontal target and actual velocity; z_error is the squared vertical velocity, whose target is 0.

1
xy_error = torch.sum(torch.square(command[:, :2] - actual[:, :2]), dim=1)
z_error = torch.square(actual[:, 2])

2Turn it into a reward between 0 and 1

The summed error is divided by std squared and passed through a negative exponential, giving 1 at zero error; zero_non_finite records numerically invalid results as 0.

2
return zero_non_finite(torch.exp(-(xy_error + z_error) / std**2))

The excerpt comes from microduck/mdp/rewards.py of the pinned Isaac Lab. command is the target velocity, actual the actual velocity and std corresponds to \(\htmlData{sym=sigma_v}{\sigma_v}\). At the start of training the linear-velocity tracking weight is 2.0 and the action-rate penalty −0.1. For long runs, also check the curriculum settings: the action-rate penalty grows as training progresses. These values are tuned for this task; another robot needs its own.

When checking a reward design, look at behavior before the total. If reward rises while falls become more frequent, inspect velocity, posture, action-change and termination terms one by one to find which term hides the problem.

Why PPO: limit how far each update moves the policy#

If a policy update is too large, a balance behavior just learned can disappear in the next sampling round. PPO (Proximal Policy Optimization) clips its surrogate objective so that very large probability changes earn no extra benefit. It suits continuous joint control and collects data easily from many parallel simulations; we use the RSL-RL implementation, so formulas, configuration and training logs line up. PPO makes updates more stable, but a single update can still make behavior worse.

First estimate how much better an action was than the average expectation in that state: the advantage. A positive advantage pushes the probability of that action up, a negative one pushes it down. The value network \(\htmlData{sym=V}{V}\) provides a baseline for the state's return; generalized advantage estimation (GAE) combines multi-step temporal-difference errors to balance bias and variance.

Temporal-difference error and generalized advantage estimation
\[\htmlData{sym=delta_t}{\delta_t}=\htmlData{sym=r_t}{r_t}+\htmlData{sym=gamma}{\gamma}\htmlData{sym=m_t}{m_t}\htmlData{sym=V}{V}(\htmlData{sym=s_next}{s_{t+1}})-\htmlData{sym=V}{V}(\htmlData{sym=s_t}{s_t}),\qquad \htmlData{sym=A_hat}{\hat A_t}=\htmlData{sym=delta_t}{\delta_t}+\htmlData{sym=gamma}{\gamma}\htmlData{sym=lambda}{\lambda}\htmlData{sym=m_t}{m_t}\htmlData{sym=A_next}{\hat A_{t+1}}\]

\(\delta_t\)
Temporal-difference error: how much better this step turned out than the value network predicted.
\(r_t\)
Immediate reward of the current control step: the weighted sum of all reward terms.
\(\gamma\)
Discount factor: closer to 1 gives more weight to distant rewards; the course training uses 0.99.
\(m_t\)

\(V\)
Value network: estimates the discounted return from a state.
\(s_{t+1}\)

\(s_t\)

\(\hat A_t\)

\(\lambda\)

\(\hat A_{t+1}\)

\(\htmlData{sym=m_t}{m_t}\) is 0 when the episode terminates and 1 otherwise; \(\htmlData{sym=gamma}{\gamma}\) discounts future rewards and \(\htmlData{sym=lambda}{\lambda}\) weights multi-step errors. Truncation at the time limit means something different from a fall: the implementation bootstraps the value separately for truncation. The course training uses \(\htmlData{sym=gamma}{\gamma} = 0.99\) and \(\htmlData{sym=lambda}{\lambda} = 0.95\).

PPO clipped surrogate objective
\[\htmlData{sym=rho}{\rho_t}(\htmlData{sym=theta}{\theta})=\frac{\htmlData{sym=pi_theta}{\pi_\theta}(\htmlData{sym=a_t}{a_t}\mid \htmlData{sym=o_t}{o_t})}{\htmlData{sym=pi_old}{\pi_{\theta_{\mathrm{old}}}}(\htmlData{sym=a_t}{a_t}\mid \htmlData{sym=o_t}{o_t})},\qquad \htmlData{sym=L_clip}{L^{\mathrm{CLIP}}}=\htmlData{sym=E_t}{\mathbb E_t}\!\left[\htmlData{sym=min}{\min}\!\left(\htmlData{sym=rho}{\rho_t}\htmlData{sym=A_hat}{\hat A_t},\htmlData{sym=clip}{\operatorname{clip}}(\htmlData{sym=rho}{\rho_t},1-\htmlData{sym=epsilon}{\epsilon},1+\htmlData{sym=epsilon}{\epsilon})\htmlData{sym=A_hat}{\hat A_t}\right)\right]\]
Variable meanings
\(\rho_t\)
Probability ratio: the probability density of the same sampled action under the new and old policies.
\(\theta\)
Parameters (weights) of the policy network, updated during training.
\(\pi_\theta\)
Policy: the neural network, set by its parameters, that maps an observation to a probability distribution over actions.
\(a_t\)
Action actually sampled at the current control step.
\(o_t\)
Observation at the current control step.
\(\pi_{\theta_{\mathrm{old}}}\)

\(L^{\mathrm{CLIP}}\)
PPO clipped surrogate objective, which training increases.
\(\mathbb E_t\)

\(\min\)

\(\hat A_t\)

\(\operatorname{clip}\)

\(\epsilon\)

\(\htmlData{sym=rho}{\rho_t}\) is the ratio of the probability densities of the same sampled action under the new and old policies, and \(\htmlData{sym=epsilon}{\epsilon} = 0.2\) sets the clip range. Clipping acts only on the objective: the ratio itself can still leave that range, and joint angles are not constrained by it.

Switch the advantage between +1 and −1 and move the ratio slider. The objective takes the smaller of the two terms, so the plateau appears on one side only, depending on the sign of the advantage. The figure analyses a single sample's policy objective; a real update also depends on the other samples, the value loss and the entropy term.

Python · core excerptFull source ↗

1Ratio of new to old policy

Subtracting log-probabilities and exponentiating gives the ratio for the same action under the new and old policies.

1
ratio = torch.exp(
    actions_log_prob - torch.squeeze(batch.old_actions_log_prob)
)

2Limit the update

The advantage and the ratio form the surrogate objective; clipping the ratio limits overly large policy changes.

2
surrogate = -torch.squeeze(batch.advantages) * ratio
surrogate_clipped = -torch.squeeze(batch.advantages) * torch.clamp(
    ratio, 1.0 - self.clip_param, 1.0 + self.clip_param
)

3Aggregate the loss

The code takes the larger of the negated terms and averages over samples; the optimizer minimizes this loss.

3
surrogate_loss = torch.max(surrogate, surrogate_clipped).mean()

In the code, ratio is \(\htmlData{sym=rho}{\rho_t}\), batch.advantages is \(\htmlData{sym=A_hat}{\hat A_t}\) and clip_param is \(\htmlData{sym=epsilon}{\epsilon}\). Because the optimizer minimizes, the implementation negates the objective and uses max, which matches “maximize the min” in the formula. The old policy's log-probabilities are stored at sampling time and stay fixed during the update.

Total loss actually optimized
\[\htmlData{sym=L_total}{\mathcal L}=-\htmlData{sym=L_clip}{L^{\mathrm{CLIP}}}+\htmlData{sym=c_V}{c_V} \htmlData{sym=L_V}{L_V}-\htmlData{sym=c_H}{c_H}\htmlData{sym=E_t}{\mathbb E_t}[\htmlData{sym=H}{H}(\htmlData{sym=pi_theta}{\pi_\theta}(\cdot\mid \htmlData{sym=o_t}{o_t}))]\]
Variable meanings
\(\mathcal L\)
Total loss actually minimized by the optimizer.
\(L^{\mathrm{CLIP}}\)
PPO clipped surrogate objective, which training increases.
\(c_V\)
Value-loss coefficient; 1.0 in this configuration.
\(L_V\)
Value loss: the error of the value network's return prediction.
\(c_H\)
Entropy coefficient; 0.01 in this configuration.
\(\mathbb E_t\)
Average over the time steps in this batch.
\(H\)
Entropy: how random the action distribution is; this term encourages continued exploration.
\(\pi_\theta\)
Policy: the neural network, set by its parameters, that maps an observation to a probability distribution over actions.
\(o_t\)
Observation at the current control step.

The value loss \(\htmlData{sym=L_V}{L_V}\) trains return prediction and the entropy \(\htmlData{sym=H}{H}\) encourages exploration. The configuration uses a value-loss coefficient of 1.0, an entropy coefficient of 0.01 and value clipping. The learning rate starts at 0.001 and then adapts to the KL divergence; you can check all of these in agent.yaml in the output folder.

Theory: PPO paper; implementation: RSL-RL 5.5.1 algorithms.

Where training data comes from and what the settings mean#

PPO needs no downloaded dataset: its training data is produced by the simulation during training. The full training in Section 3.2 starts from a random initialization and reads no weights from the fixed walking model. The script creates 1024 Newton environments from the Isaac Lab task configuration, and each environment collects 24 interaction steps per iteration. Each record holds the observation, action, reward, old-policy log-probability, value estimate and termination flag; records live in a GPU memory buffer and are replaced by the next iteration's data.

Samples per iteration and in total
\[\htmlData{sym=N_batch}{N_{\mathrm{batch}}}=\htmlData{sym=N_env}{N_{\mathrm{env}}}\times \htmlData{sym=T_rollout}{T}=1024\times24=24576,\qquad \htmlData{sym=N_total}{N_{\mathrm{total}}}=2500\times24576=61{,}440{,}000\]
Variable meanings
\(N_{\mathrm{batch}}\)
Number of samples collected per training iteration.
\(N_{\mathrm{env}}\)
Number of parallel environments; 1024 in the full training of Section 3.2.
\(T\)
Control steps collected per environment per iteration; 24 in Section 3.2. It is a different quantity from the episode time limit.
\(N_{\mathrm{total}}\)
Total samples collected over 2500 iterations.

This budget produces about 61.4 million environment interactions and 2500 × 5 × 4 = 50,000 optimizer updates. At the 50 Hz control rate that is about 341 hours of simulated “practice”; parallel environments on the GPU collect it in about 2 hours. A training environment is reset on its own when its episode terminates while the others keep sampling.

1Create the training environment

Build the task and wrap it as a vectorized environment so the algorithm reads observations and rewards from all environments at once.

1
base = gym.make(task, cfg=cfg).unwrapped
env = RslRlVecEnvWrapper(base, clip_actions=agent.clip_actions)

2Connect the PPO runner

Give the runner the environment, algorithm settings, output folder and device.

2
runner = OnPolicyRunner(
    env, to_dict(agent), log_dir=str(args.output), device="cuda:0"
)

3Learn for a fixed number of iterations

The iteration count sets this run's budget; random initial episode lengths spread out the environments' terminations.

3
runner.learn(
    num_learning_iterations=args.iterations, init_at_random_ep_len=True
)

The Isaac Lab task provides state transitions, managers and batched resets; the wrapper connects it to RSL-RL, and OnPolicyRunner repeats sampling and updates. Newton's Warp/CUDA path advances these environments in parallel on the GPU; the speed comes from batched execution and a single task interface.

Checkpoints, configuration and exported files#

Training writes several kinds of files to the output folder. initial.pt stores the starting point, model_*.pt are training checkpoints saved every few hundred iterations, env.yaml and agent.yaml record the environment and optimizer settings actually used, and exported/policy.onnx is the file for inference. A checkpoint can include optimizer state; an ONNX file usually keeps only the inference graph. They serve different purposes and cannot replace each other.

The reward combines velocity tracking, posture, smoothness and contact terms. Two policies with the same total reward might earn it differently: one by tracking speed more accurately, the other by moving less and staying stable. So check actual behavior and the individual terms together.

Check your understanding

Can you resume training exactly from an ONNX file alone?

Show explanation

No. Exact resumption also needs optimizer state, normalization state, random state and the same configuration, so keep the full checkpoint and training configuration.

Check your understanding

Why not report the highest return seen during training as an independent test result?

Show explanation

That result already took part in learning or model selection, and a high reward does not necessarily mean task success. An independent test fixes the scenarios and success criteria in advance and counts every result under conditions not used for selection.
