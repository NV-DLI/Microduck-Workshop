任务：把图像中的目标变成可用观测

行走策略知道如何控制身体，却不知道足球在哪里。Isaac Sim 可以在同一 USD 场景中让 RTX RGB、深度和机器人头部姿态按统一时钟更新，便于重复检查视角、遮挡与时间对齐。本章先理解检测器如何在图像中找出足球与球门，以及这些二维结果如何与 ToF、IMU 和头部运动学结合。目标检测回答“是什么、在图像中的哪里”；距离、方向和观测是否仍有效，则需要额外的几何与时间信息。

之所以选择学习型检测器，是因为目标大小、视角和背景都会变化。与手工设定颜色阈值相比，检测模型可以从标注样本中学习特征；代价是需要覆盖目标条件的数据和独立验证。Isaac Sim 支持在受控场景中生成图像和标注，适合系统改变相机位姿、光照和遮挡；但当前课程传感器 rig 明确不输出物体语义真值，练习集标签也不是运行时从场景自动读取。这里先使用固定模型作为基准，再用现有小数据集体验训练。

从图像中的位置，到机器人能使用的位置

检测器回答的是“球出现在画面的哪里”，导航需要的却是“球在机器人前方多远、左侧或右侧多远”。像素坐标没有米制距离，不能直接送给路径规划器。这里把图像检测、相机参数、头部姿态与距离信息结合起来，转换成相对于机器人坐标系的位置。

一个像素只能确定一条视线；要知道球沿这条视线离相机多远，还需要球体尺寸、地面约束或测距等信息。实际任务还会检查相机姿态与图像时间是否一致。先掌握输入和输出的关系，下面的推导可在需要实现或排查定位误差时展开阅读。

拓展：像素射线、距离公式与实现细节

单个像素只能确定一条观测方向，不能直接给出距离。先用内参矩阵 K 将像素坐标反投影到相机坐标系，再用相机外参把射线转换到所需坐标系。下面以“射线与地面相交”为例，说明几何约束如何提供尺度；实际足球中心高于地面，必须使用与球体和相机相符的几何模型，不能把边界框中心直接视为地面接触点。

针孔相机的反投影
\[\widetilde{\mathbf d}_C=K^{-1}[u,v,1]^{\mathsf T},\qquad \mathbf d_B=R_{BC}\frac{\widetilde{\mathbf d}_C}{\|\widetilde{\mathbf d}_C\|},\qquad \mathbf p_B=\mathbf o_B+\lambda\mathbf d_B\]
已知平面时的射线交点
\[\mathbf n^{\mathsf T}\mathbf p+d_0=0\quad\Rightarrow\quad\lambda=-\frac{\mathbf n^{\mathsf T}\mathbf o+d_0}{\mathbf n^{\mathsf T}\mathbf d}\]

分母接近 0 时，射线与平面几乎平行；λ ≤ 0 时，交点不在射线前方。遇到这些情况应拒绝该结果，而不是强行给出距离。相机姿态还必须与图像采集时刻对齐；头部转动后若用新姿态解释旧图像，会引入偏差。

Python · 几何原理示意，不是独立运行脚本
ray_camera = inv_K @ np.array([u, v, 1.0])
ray_camera /= np.linalg.norm(ray_camera)
ray_body = R_body_camera @ ray_camera
denominator = normal @ ray_body
# 使用交点前，检查分母是否接近零以及距离的符号。
distance = -(normal @ origin + plane_offset) / denominator
point_body = origin + distance * ray_body

这段示意代码用于对应公式；完整任务还会使用 Isaac Sim RTX 图像、32 × 32 深度图采样得到的 8 × 8 ToF 近似、头部运动学和有效性检查。传感器挂载到实际 Newton 头部连杆姿态，而不是保持世界水平的虚拟云台。验证时，应同时检查检测框、相机内参、估计位置和时间戳；检测框正确并不意味着三维位置一定正确。

从一个像素到一条空间射线

在光学相机坐标系中，像素 \( (u,v) \) 对应的射线方向与 \( [(u-c_x)/f_x,\,(v-c_y)/f_y,\,1]^{\mathsf T} \) 成比例。内参中的 \(f_x,f_y\) 是以像素为单位的焦距，\(c_x,c_y\) 是主点。射线只表示方向；确定距离还需要已知几何或其他传感器提供约束。

相机坐标系通常规定 x 轴向右、y 轴向下、z 轴向前；本课程的机身坐标系则规定 x 轴向前、y 轴向左、z 轴向上。两者之间必须依据相机相对于机身的旋转和平移进行变换，不能直接把同名坐标轴上的数值相加。头部转动也会改变这一变换，因此目标定位必须使用对应时刻的头部关节状态。

ToF 的 8 × 8 距离网格并不是 64 个独立的物体标签。单个网格可能同时覆盖地面和球，近距离反射也可能产生无效读数。应先检查测距状态和有效范围，再判断这些数据能否支持图像中的目标。若把“没有有效测量”误解为“前方没有障碍”，后续导航就会建立在错误前提上。

曾经看见，不等于现在仍然知道

机器人移动或低头后，球可能暂时离开画面。虽然可以利用里程计在短时间内更新球的相对位置，但这种记忆会不断累积误差。一旦观测过期、ToF 数据无效或地面约束丢失，就应停止移动并重新观察，不能把缺失数据当作空地。

检查理解

检测器画出了准确的球框，就可以直接把球框中心当作世界坐标吗？

查看解析

不能。像素位置只能表示图像中的方向，还需要相机模型、相机姿态以及距离或几何约束，才能估计目标的空间位置。

目的地不是球心

射门的目标是让脚把球送向球门，而不是让机身占据球心。直接把球心交给导航器，可能导致提前撞球，或从无法出脚的一侧接近。因此，先从最终动作反推准备站位：机器人面向球门，在球后留出距离，再为踢球脚留出横向偏移。

“站在球后方”是人为设计的任务先验。设计者根据射门方向、机器人尺寸与技能可用范围写出规则；当前系统没有让行走网络自行理解足球规则。检测模型学习目标外观，行走与踢球策略学习运动；站位计算使用明确的几何关系，Nav2 再为给定目标寻找路径。

要区分“相对偏置”和“地图坐标”。某一阶段可以采用固定的准备距离与横向偏移，但球的位置或射门方向一变，目标坐标就会重新计算。当前室内任务使用视觉估计球的位置，并把已知球门位置和场地边界作为显式地图先验；它不是在未知球场中自动发现全部地图。

从球与球门算出位置和朝向

先把足球位置 B 和球门中心 G 放在同一平面坐标系中，单位均为米。用球指向球门的单位向量 u 表示射门方向，用 n 表示朝该方向看时的左侧。下面的角度从地图 +x 轴逆时针计量。

射门方向与左法向
\[\mathbf u=\frac{\mathbf G-\mathbf B}{\|\mathbf G-\mathbf B\|},\qquad \mathbf n=\begin{bmatrix}-u_y\\u_x\end{bmatrix}\]
准备位置与目标朝向
\[\mathbf P^*=\mathbf B-d\mathbf u+\ell\mathbf n,\qquad \theta^*=\operatorname{atan2}(u_y,u_x)\]

d 是沿射门方向后退的距离，ℓ 是机器人向左偏移的距离。为何这样相加？到位并面向球门后，球相对机身的位置应约为 (d, −ℓ)，因此 B = P* + d u − ℓ n，移项就得到上式。ℓ > 0 表示机器人左偏、球在身体右侧，有利于右脚对球；它不是球也向左偏。B 与 G 重合时方向没有定义，应拒绝该输入。

例如 B = (0.02, 0)、G = (0.68, 0)，取 d = 0.22、ℓ = 0.035，则 u = (1, 0)，得到 P* = (−0.20, 0.035) m、θ* = 0°。机器人停在球后 22 cm，并向左偏 3.5 cm。若球横移，方向与目标都要按新观测重算；不是把这个地图坐标永久保存为射门点。

Nav2 如何把目标变成路径

Nav2 是开源的 ROS 2 导航框架。本实验使用其中的 Navfn 规划器：输入机器人起点、目标位姿和代价地图，返回一串路径点。导航准备点由上面的任务规则提供；Nav2 本身不知道什么是右脚射门。查看 Nav2 开源项目。

占据栅格把空间分成已知空地、障碍和未知区域；代价地图进一步表达通行代价。靠近障碍的格子代价更高，可以让路径保留余量。机器人有体积，还要检查路径周围的外形包络，不能只检查一根没有宽度的线。

当前配置明确启用 A* 搜索。理解其直觉时，可以用“已经付出的路径代价 + 到终点的估计剩余代价”比较候选格子。下面是 A* 的概念公式，帮助解释为何搜索会朝目标推进；它不是 Navfn 内部势场更新与路径提取的逐行实现。

A* 的概念评分
\[f(n)=g(n)+h(n)\]

这里 g(n) 是到候选格子 n 的累计代价，h(n) 是从该格子到目标的估计代价；公式中的 g、n 与上一节的球门 G、法向向量 n 属于不同语境。实际使用哪个搜索算法由配置决定，不是行走网络学习出的选择。

完整任务将带时间戳的观测、已知场地边界、机器人位姿和目标组成不可变快照，由桥接程序提交给独立 CPU 容器内的 ROS 2 Jazzy Nav2 服务。服务发布对应地图与坐标变换，再调用 ComputePathToPose；返回结果必须与请求序号、坐标系及地图快照一致。当前地图结合 ToF 观测与已知空场先验，尚不能证明未知场景建图或任意障碍避让能力。

有了路径，机器人如何真正走过去？

在常见 Nav2 系统中，控制服务器可以跟踪路径并发布速度；本实验没有启用这条完整执行链。当前桥接器取得 Navfn 路径与通行检查结果，自有控制器再结合视觉球方位、准备点误差和身体姿态，生成有限的转向、前进、对齐或停止阶段。因此不能把视频解释为“Nav2 自带控制器严格逐点跟踪路径”。

从机身命令到关节动作
\[\mathbf c_t=(v_x^{\rm cmd},v_y^{\rm cmd},\omega_z^{\rm cmd}),\qquad \mathbf a_t=\pi_{\rm walk}(\mathbf o_t,\mathbf c_t)\]

机身命令表示期望怎样移动；行走策略把命令与本体观测组合起来，输出 14 维关节动作。策略以 50 Hz 更新，Newton 以 200 Hz 推进物理。命令值不等于实际达到的速度：步态、接触和延迟都会造成误差，所以还要看新观测与身体状态。转向的正负号和速度缩放应以执行器接口为准。

检查理解

Nav2 已返回一条有效路径，但机器人还在转向。此时能声称“已到达射门站位”吗？

查看解析

不能。路径只是规划结果。需要检查实际位置、朝向、姿态与观测，再单独核验出脚条件；行走命令本身也不是实际到达的证据。

Isaac ROS 与 Nav2 是什么关系？

Nav2 是独立的开源导航框架，并非 NVIDIA 的专有导航器。Isaac ROS 是 NVIDIA 提供的加速 ROS 组件集合，可以向 Nav2 提供感知、定位和环境表示。例如，Isaac ROS Visual SLAM 可提供位姿，nvblox 可根据深度与位姿构建环境表示，再通过代价地图接口支持 Nav2 规划。更准确的名称是 “Isaac ROS 与 Nav2 集成导航”，不是把两者当作同一个产品。

本实验实际使用 Isaac Sim + ROS 2 Nav2，尚未使用 Isaac ROS 包。Isaac Sim 提供 RTX 传感器渲染，Isaac Lab 组织学习任务与策略接口，Newton 推进物理；Nav2/Navfn 在 CPU 容器中规划，自有控制器完成阶段与命令交接。使用 Isaac Sim 不会自动意味着使用了 Isaac ROS。导航依赖和启动入口可在 软件包锁定文件与 服务源码中核对。

若将来要把这条链路扩展到真实设备或更复杂场地，应先确定需要改进的是定位、建图还是控制，再选择组件，并重新检查接口、延迟与任务成功率。Nav2 官方视觉导航教程展示了 NVIDIA 组件与 Nav2 的协同；那套平台的传感器和计算配置不能直接视为 Microduck 已具备的配置。

把接近分成几个阶段

  1. 1搜索与观察
  2. 2远距离接近
  3. 3近距离对准
  4. 4检查出脚条件
  5. 5踢球与恢复

距离较远时，可以优先缩短与球之间的距离；接近后则应减小移动幅度，同时检查球是否仍然可见、机身朝向是否正确，以及脚掌与球的相对位置是否合适。即使距离已经足够近，只要朝向不正确，就仍不应出脚。

导航规划器负责给出路线或方向，行走策略负责实际执行。规划器找到可行路径，并不代表机器人已经沿该路径走完全程；Isaac Sim 的可重复场景便于同时回看相机、俯视轨迹和物理接触，完整系统仍必须处理策略跟踪误差、执行器延迟、接触事件和传感器更新。

手算一次出脚站位

先用球门中心减去球的位置，得到从球指向球门的方向，再将该方向归一化。站位位于球的后方：从球的位置沿该方向反向移动 distance，再沿垂直方向偏移 lateral，为出脚腿留出空间。偏移方向是这项几何练习中的约定，不能直接替代真实技能入口的标定值。

先运行第 7 章的站位计算命令。打开生成的 plan.svg，检查目标点、球和球门之间的相对关系；plan.json 中记录了目标坐标与朝向。把距离从 0.18 改为 0.25，并使用另一个输出目录：先预测目标点会向哪个方向移动，再用结果验证预测。该命令只计算已知点之间的几何关系，既没有运行物理仿真，也不能证明目标实际可达。

完整任务还需要应对机身偏航漂移、步态延迟以及近距离目标离开视野等情况。因此，接近过程中必须持续更新观测并检查停止条件。当有效距离信息或地面支持丢失时，应先停止或在约束下后退，再重新观察；未知区域不能直接当作空闲区域。

什么时候需要再看一眼

一次观察可以给出起始目标，但机器人走动后，相对位置会变化，姿态与里程估计也会积累误差。相机低头找球、抬头看球门，解决的是视野与精度问题；必要时再观察，比把过期位置当成当前事实更可靠。这里保留出脚前的位置核验。后退仅在观察或站位条件不足时作为恢复选项，正常成功流程可以直接接近并射门。
