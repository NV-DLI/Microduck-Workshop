# 4.2 手工设计的射门阶段

:::{lesson-intro}
:meta: 第 4.2 节 · 预计学习时长 25 分钟

射门为什么采用板载策略，传感器估计、路径规划和运动技能怎样由手工设计的阶段连接起来，以及怎样在 Isaac Sim 中自动重复射门。
:::

{#why}
## 为什么采用板载策略

Microduck 公开的硬件使用 Rockchip RK3566 计算，其中的小型神经网络加速器（NPU）为单核 INT8，算力 0.8 TOPS；运动策略以 50 Hz 循环运行（[官方 README ↗](https://github.com/pollen-robotics/microduck)，[NPU 说明 ↗](https://github.com/pollen-robotics/microduck/blob/main/docs/project/npu-bringup.md)）。这样的算力难以承担 GR00T 这类约 30 亿参数的视觉-语言-动作模型的低延迟推理。因此这里选择小型检测器，配合几何计算、路径规划和已训练的行走与踢球技能。

本课程在工作站上以仿真运行这套设计。它展示的是板载方案的思路，不是对机器人自身计算机的测量。

{#pipeline}
## 从传感器到动作：Isaac Lab + Nav2

这里有两个独立的工具协同工作。**Isaac Lab**（基于 Isaac Sim，物理引擎为 Newton）仿真机器人、传感器和球场，并运行学到的策略。**Nav2** 是 ROS 2 的导航框架；课程只用它的路径规划器，作为同一容器里的一个 CPU 进程运行。课程代码把机器人的位置（在已知球场地图上由传感器估计）和目标点交给 Nav2，再拿回一串路径点。地图是预先给定的；机器人并不靠 8 × 8 ToF 为未知环境建图。

| 组成部分 | 做什么 |
|---|---|
| YOLO26n 检测器 | 在 RGB 图像中框出球和球门 |
| 几何计算 | 由方框、ToF 地面和关节角算出球与球门的位置 |
| Nav2 规划器（NavFn，A*） | 在二维代价地图上找到一条到球后站位的低代价路径 |
| 路径跟随与阶段 | 把下一个路径点变成行走速度；按条件切换阶段 |
| 行走策略 | 把速度请求变成 14 个关节目标，50 Hz |
| 踢球与恢复 | 出脚击球，再回到站立 |

Nav2 返回的是地面上的点，从不输出关节角。一段简短的手写跟随程序把下一个路径点变成速度请求，平衡和迈步交给行走策略完成。

{#stages}
## 射门的六个阶段

```{learning-flow}
label: 板载策略的步行射门阶段
nodes:
- [寻找目标, 转头观察球门与足球]
- [规划接近, 选好球后站位，分段走近]
- [近距细调, 小步移动，停稳后再看球]
- [对准出脚位置, 球在右脚前，身体朝向球门]
- [交接给踢球, 停步，头部回正，身体静止]
- [踢球与恢复, 踢球技能出脚，回到站立]
details:
- 转头寻找球门和足球，确定自己相对球门的位置。信息过旧或互相矛盾时，停下来重新观察。
- 由球和球门的位置算出射门方向，在球后方、偏向右脚的位置选出站位。Nav2 规划到站位的路径，跟随程序分段走过去；途中定期重新确认球门。
- 离球较近后改为小步移动或原地转向。每走一段就停稳，等身体晃动减小后再看球，因为行走时相机在晃，测得的位置不够准。
- 检查球是否落在右脚前方、身体是否朝向球门。不满足就回到细调。
- 停止行走，头部回到踢球姿态，并确认身体已经静止、球门信息仍然新鲜，才把控制交给踢球技能。
- 运行踢球与恢复技能，随后回到站立。是否进球由评测程序用仿真真值判断。
layout: learning
loop: false
```

阶段之间不是按时间切换，而是看条件：条件不满足，策略就停下、重新观察或退回上一阶段，所以一次射门中细调常会重复好几次。

{#training}
## 哪些经过训练，哪些没有

- **检测器。** YOLO26n 模型用 Isaac Sim 渲染的图像微调。方框标注根据已知的场景几何自动生成；512 张用于训练，128 张用于挑选检查点，另外 128 张留作测试（mAP50 0.978）。这是图像检测指标，不是射门成功率。
- **行走。** 行走策略用 PPO 训练，也就是第 3 部分的方法。
- **踢球。** Pollen Robotics 提供的踢球与行走策略保持冻结，作为教师；一个用 PPO 在 Isaac Lab 中训练的小型残差网络，在其上叠加有界的修正。
- **没有训练的部分。** Nav2 规划器、几何计算、路径跟随和阶段逻辑都是配置或编写出来的。整个射门从未端到端训练。

{#run}
## 自动重复板载射门

先按 [1.2 节](setup.md) 准备好课程容器，再回到容器终端；容器已在运行时，可以在宿主机用 `docker exec -it microduck-workshop bash` 进入。然后运行：

```{code-block} bash
:caption: Terminal · 容器内
:class: terminal

python3 scripts/run.py football --repeat 5 --seconds 45 --no-record-hd --output outputs/onboard-football-repeat
```

| 参数 | 含义 |
|---|---|
| `--repeat 5` | 连续尝试五轮；`--repeat 0` 会一直重复，直到按下 **Ctrl+C** |
| `--seconds 45` | 每次射门的时间上限，单位是仿真秒 |
| `--no-record-hd` | 不录制额外的 1080p 第三人称存档视频；保留传感器面板、任务日志和评分 |
| `--output` | 一个新目录；每次射门在其中写入自己的 `episode-001`、`episode-002` 等目录 |

每次射门结束后 Isaac Sim 会关闭，再为下一次重新打开，所以每一次都从相同的起始姿态重新开始。机器人走、停、看时，对照 RGB 和 ToF 面板观察。

每次射门后，终端会显示成功或失败原因，最后一行统计成功与失败次数；失败的射门会被计入，不会被跳过。按 **Ctrl+C** 会停止当前射门，并且不再开始下一次。崩溃或独立检查未通过等技术错误也会停止循环；这次射门的文件会保留，但不计入成功或失败。窗口通常比真实时间慢，因为工作站要渲染场景和传感器；这个速度不能说明机器人自身计算机的速度。

:::{course-image} media/isaac-ui-onboard-sensors.png
:alt: 板载射门的 Isaac Sim 完整界面，同时显示绿色球场、头部 RGB 图像和 8×8 ToF 距离。

左侧观察机器人，右侧对照它此刻看到的图像与距离。NR 表示没有回波，不能据此认为前方没有障碍。
:::

:::{enrichment} 代码关键参数
- **重复运行。** `scripts/repeat_episodes.py` 让每次射门在独立的进程组中运行，并在 `--output` 目录中写出 `summary.json`。第一次射门使用默认的 `--seed`，之后每次加一，这会改变仿真的传感器噪声；起始姿态保持不变。`--root-y` 可以改变机器人的横向起始位置（默认 0.04 米）。不加 `--repeat` 时，`run.py football` 和以前一样只运行一次。
- **启动。** 每次射门都先把关节锁定在 HOME 姿态、身体自由地站在地面上，等传感器和行走策略的第一次输出就绪后，在应用这次输出之前解除锁定。
- **场景。** `lab/onboard_scene.py` 创建绿色球场并执行这种启动；`--scene indoor` 与 `--style A` 是 `run.py football` 的默认值。
- **行走策略。** 仓库的 `models/walk.onnx` 复制为容器内的 `/workspace/state/student-course/simulation/core/models/reference/velstand.onnx`，由 `--model` 加载。
- **检测器。** `run.py` 先核对 `models/scene-detector/deployment.json` 所列权重的 SHA-256，再写出 `/workspace/state/scene-detector-deployment.json`，经 `--detector-deployment` 加载。
- **Nav2。** `lab/scene_nav2/nav2.yaml` 把 NavFn 规划器配置为 A*，使用 2.5 厘米分辨率、按机器人半径膨胀的代价地图；`lab/runtime/simulation/core/football/controller.py` 把返回的路径变成速度请求。
- **踢球与恢复。** 执行器从固定路径 `/workspace/state/student-course/configuration/core/kick_policy/export/deployment.json` 加载，它绑定由 `models/kick-teacher.onnx` 和 `models/kick-residual.onnx` 复制的两个网络。
:::

{#results}
## 已记录的结果

为了观察起始位置对流程的影响，课程事先固定了一组检查：机器人相对足球取五个横向起点，每个起点尝试一次，不打开窗口，并使用 `--no-record-hd`。你的 `--repeat` 运行始终使用同一个起点，所以请以你自己的统计为准，不要期待得到相同的数字。

```{benchmark-chart}
title: 五个横向起点，每个起点一次板载射门
caption: 每一行是相对足球的一个起始位置，各尝试一次。完全成功指脚触球、整球进门并恢复站立。一块球场上的五次尝试只是一个小检查，不是一般意义上的成功率。
```

| 横向起点 | 完全成功 | 摔倒 | 结束方式 |
|---|---|---|---|
| −4 厘米 | 1 / 1 | 0 / 1 | 31.5 秒进球，恢复站立 |
| 0 厘米 | 1 / 1 | 0 / 1 | 14.5 秒进球，恢复站立 |
| +4 厘米（实验默认） | 0 / 1 | 0 / 1 | 在近处反复重新观察，直到该阶段超时 |
| +8 厘米 | 0 / 1 | 0 / 1 | 踢球被拒绝；安全检查未通过后停止 |
| +12 厘米 | 1 / 1 | 0 / 1 | 28.1 秒进球，恢复站立 |

这组尝试的成功率是 **3/5（60%）**，成功均包括进球并恢复站立，没有一次摔倒。两次失败都在脚触球之前结束，各对应下面一种情况。记录呈现的是观察到的过程，尚不能据此确定根本原因：

- **近处位置无法确认。** 接近球后，未能持续得到足以用于对准的可靠位置，于是一直停留在重新观察阶段，直到该阶段超时。这段时间里检测器仍然框出了足球，被反复拒绝的是由方框算出的位置。
- **出脚条件未满足。** 球落在踢球技能训练时覆盖的范围之外，踢球被拒绝。后退调整时感知安全检查未通过，机器人停止尝试。

如果你的某次射门失败，还可以检查 **没有可用路径**（Nav2 找不到到站位的安全路径）和 **踢球时的平衡**。`summary.json` 列出每次射门的结果；单次射门 `manifest.json` 中的 `terminal_reason` 记录了结束它的阶段。

{#design}
## 这些阶段从哪里来

每个阶段和切换条件，都来自我们对射门这个任务的理解：踢球技能需要球在右脚前、身体朝向球门，所以要站位和对准；行走时看不准，所以要走、停、看交替；踢球要从静止站姿开始，所以要单独交接。

这样的流程清楚、容易排查，但只适合这一个任务。换成“把球带到中圈停下”或“走到球旁但不要碰球”，阶段、条件和阈值大多要重新设计。如果模型推理可以离开机器人，放到 GPU 工作站上，或以更多网络延迟为代价放到云端服务器上，就能使用大得多的视觉-语言-动作模型：它从语言指令和示范中学习，而不是依靠手写的阶段，快速控制仍由已训练的运动技能负责。第 5 部分在本地工作站上用 GR00T 走这条路线，示范来自这里的板载策略。

::::{quiz}
板载射门中，哪些部分是从数据中学到的，哪些是人编写或配置的？

:::{answer}
检测器、行走策略和踢球残差经过训练。几何计算、Nav2 路径规划、路径跟随和阶段逻辑是配置或编写的，整个射门从未端到端训练。
:::
::::

::::{quiz}
想让 Microduck 把球带到中圈停下，现有的板载策略能直接复用吗？

:::{answer}
感知部分大多可以复用，但站位、阶段顺序、切换条件和交接都是为射门设计的，需要重新设计和调试。为每个新任务手工重写流程，正是第 5 部分转向从示范中学习的原因。
:::
::::
