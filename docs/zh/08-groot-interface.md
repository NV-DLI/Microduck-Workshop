# 5.2 使用 GR00T 自主完成射门

:::{lesson-intro}
:meta: 第 5.2 节 · 预计学习时长 30 分钟

GR00T 怎样完成步行射门：它读什么、输出哪 8 个高层请求、由谁执行，各模块多久更新一次，以及示范数据、动作头训练和闭环验证的思路。GR00T 的训练和推理都由课程预先完成，本节不需要动手运行。
:::

```{symbols}
H:
  tex: H
  text: 一次预测的高层请求步数；本节为 16。
K:
  tex: K
  text: 每次预测后实际执行的请求步数；本节为 4。
T_exec:
  tex: T_{\mathrm{execute}}
  text: 执行一段请求覆盖的仿真时长；本节为 4 ÷ 12.5 Hz = 0.32 秒，不含推理和通信耗时。
f_action:
  tex: f_{\mathrm{action}}
  text: 高层请求的记录与执行频率；本节为 12.5 Hz。
```

{#task}
## 从射门目标设计学习任务

要让 GR00T 完成射门，首先把目标说清楚：走到足球前，调整站位，用右脚把球踢进球门，最后恢复站立。接着决定模型能看到什么、可以请求什么动作，以及怎样判断一次任务完成。下面用课程中的 Microduck 方案串起这几个设计选择；同样的方法也可以用于其他机器人任务。

示范中的任务指令是：

<q>Walk to the football, kick it into the goal with the right foot, and recover to standing.</q>

图像提供球与球门的相对关系，身体状态提供当前运动情况，文本说明要完成的目标。课程用固定任务和球场来建立可检查的基线；这项实验的覆盖范围不代表 GR00T 的能力上限。要学习更多指令、起点和场景，应准备相应示范，并用未参与训练的条件检验泛化。

:::{course-video} media/groot-walking-success-recorded
:alt: GR00T 控制 Microduck 的一次步行射门仿真录像：机器人在绿色球场上走向足球，停稳后用右脚把球踢进球门，随后恢复站立。

GR00T 控制的一次步行射门：观察机器人怎样走到球前停稳、发出踢球请求，球进门后又怎样恢复站立。GR00T 只给出移动、视线和踢球这 8 个高层请求；迈步、保持平衡和出脚的关节动作由已训练的技能完成。
:::

{#reuse-skills}
## 分层控制：GR00T 决定做什么，技能负责怎样做

```{learning-flow}
label: 模型学习如何使用技能，技能负责落实运动
nodes:
- [观察与目标, 4 帧图像、127 维状态、任务指令]
- [GR00T, 预测 8 维高层请求]
- [技能执行层, 行走 / 视线 / 踢球与恢复]
- [机器人与反馈, 关节运动，重新观察]
details:
- 每 80 ms 整理一次观察：同一台板载相机的 4 张历史画面、当前与过去的身体状态，以及固定的任务指令。不包含球或球门的仿真坐标，也不包含板载策略内部的任务阶段。
- GR00T 输出一段 16 × 8 的请求：每一步包含前进、横移、转向 3 个移动请求，颈部与头部 4 个视线请求，以及 1 个右脚踢球请求。
- 官方行走策略把移动请求转换成关节动作并维持平衡；头部请求经过限幅和变化速率限制；踢球请求超过阈值后，由执行层检查停稳和姿态，再运行局部踢球与恢复技能。
- 底层以 50 Hz 持续控制关节，新的图像与身体状态用于下一次预测。
layout: learning
loop: true
```

| 序号 | 请求 | 范围 | 谁来执行 |
|---|---|---|---|
| 1–3 | 前进、横移、转向 | ±0.35、±0.20、±0.80，行走策略的原生指令值 | 官方行走策略，结合身体反馈生成 14 个关节动作 |
| 4–7 | 颈部俯仰、头部俯仰、头部偏航、头部侧倾 | 弧度，相对中性位 | 头部适配器限幅并限制变化速率后交给底层 |
| 8 | 右脚踢球 | 0～1 | 超过 0.5 时，执行层先确认停稳、头部回正，再运行约 4 秒的局部踢球与恢复技能 |

前三个数是行走策略的原生指令值，不是测得的速度；踢球值只是“现在请求出脚”的信号，不是关节角或成功概率。GR00T 学的是“什么时候往哪走、往哪看、什么时候出脚”，平衡、迈步和触球交给已经用强化学习训练好、以 50 Hz 运行的技能。这一执行层的踢球与恢复组合了参考踢球与站立策略、课程训练的残差修正和恢复逻辑，与 4.2 节板载策略只用官方策略的配置不同。

**为什么不直接输出关节角？** GR00T 一次推理的服务端计算约需 0.33 秒，而行走策略每 20 ms 就要根据身体反馈更新一次关节动作。直接控制关节，模型还要学会平衡和接触，需要更丰富的示范与严格的时序验证。代价是 GR00T 的能力受限于下面的技能：行走策略做不到的动作，高层请求也要求不来。

GR00T 每次预测 $\sym{H}$ = 16 步请求，执行端只执行前 $\sym{K}$ = 4 步，然后用新的观察重新预测：

```{formula} 一段请求覆盖的仿真时长
\sym{T_exec} = \sym{K} / \sym{f_action}
```

以 $\sym{f_action}$ = 12.5 Hz 计，4 步对应 0.32 秒仿真时间，期间每条请求保持 80 ms，行走策略在每条请求下更新 4 次。

## GR00T 读取哪些信息

| 输入 | 结构 | 说明 |
|---|---|---|
| 相机历史 | 4 张 RGB 图像，每张 270 × 480 | 同一台头部相机的当前帧，以及约 1.9、3.8、5.8 秒前的帧 |
| 任务指令 | 文本 | 上面那句固定的英文指令 |
| 数值状态 | 127 维 | 机身角速度与重力方向、关节位置与速度、上一次电机动作与高层请求、踢球技能的进度，以及与三张历史图像对应的状态摘要 |

4.1 节的板载策略同时使用 RGB 相机、ToF、关节编码器和 IMU，GR00T 只读取其中一部分：

{#data-train}
## 准备能够教会任务的示范

先让一个可用的教师完成任务，再记录“在这样的观察下，下一步应该请求什么”。教师可以来自人工遥操作，也可以来自已经验证的自动策略。本课采用板载策略产生的示范，并保留完整的接近、观察、调整、出脚与恢复过程；仅采集进球瞬间，模型就没有机会学习怎样走到可踢球的位置。

| 数据设计 | 本课的选择 | 为什么这样做 |
|---|---|---|
| 观察与标签 | 对齐 RGB、身体状态、任务文本与 8 维高层请求 | 让每个标签对应发出请求之前可获得的信息，避免读到未来状态 |
| 时间序列 | 每 80 ms 一条请求；每个训练锚点配一段 16 步标签 | 学习动作怎样连续变化，而不只是独立判断下一步 |
| 历史信息 | 当前画面与 3 张历史画面，配对相应状态摘要 | 帮助区分正在接近、转向还是恢复，历史帧只能来自过去 |
| 数据划分 | 按完整回合分成训练与验证集 | 同一回合的相邻帧太相似，不能拆到两组里制造虚假的验证效果 |
| 数据检查 | 固定维度、关节顺序、单位、时间戳和有效帧标记 | 避免网络把错误的字段或补齐的帧当成真实信息 |

新任务还应覆盖偏差与纠正：从侧面接近、球短暂离开画面、站位不合适时，教师应怎样恢复。仅增加相似的成功回合，未必能解决模型离开示范轨迹后的失败。末尾不足一个动作块时，应明确哪些标签有效，不能把填充值当成真实动作。

{#training}
## 冻结视觉语言骨干，训练动作头

预训练的视觉语言骨干负责把图像与任务文本转成特征。本课保留这些参数，训练动作头及其状态、动作投影层，让它们适应 Microduck 的 127 维状态和 8 维请求接口。这里更新完整动作头，不是只训练最后一个线性层，也不是 LoRA 微调；底层行走和踢球技能保持原有权重。

```{learning-flow}
label: 从示范训练 Microduck 的动作接口
nodes:
- [图像与文本, 冻结的视觉语言骨干]
- [状态与动作标签, 127 维状态与 16 × 8 请求序列]
- [训练动作头, 学习从带噪动作恢复示范请求]
- [闭环验证, 新起点下独立完成整个任务]
details:
- 复用预训练的视觉与语言表示，减少本课任务需要更新的参数。
- 状态与图像必须对齐；归一化统计只从训练集计算，并在部署时保持相同顺序与单位。
- 给示范动作加入噪声，动作头结合视觉语言特征与状态学习去噪方向；反向传播只更新允许训练的动作头与投影层。
- 验证时输入模型自己的执行结果，检查进球、跌倒、恢复、超时与异常。训练损失和离线动作误差都不能替代闭环任务结果。
layout: learning
```

对照示范检查预测，可以发现接口或时间对齐问题；让模型真正控制仿真机器人，才能发现动作误差是否会逐步积累。成功、失败和技术错误都应留档，并区分“正常执行但任务失败”和“程序没有完成运行”。上方视频展示一个成功回合，不能单凭它判断可靠性。

{#timing}
## 控制周期

模型决定下一段高层请求，底层策略持续处理快速的身体反馈。下面用便于阅读的整数说明两个节拍：高层每条请求覆盖 80 ms，前 4 条覆盖 320 ms；底层按理论 50 Hz、每 20 ms 更新一次关节动作。

```{control-timing}
kind: groot-theory
```

图中的 **约 300 ms** 是 DGX Spark 上服务端新推理中位数约 **332 ms** 的取整示意，不是平均值，也不包含图像采集、网络传输和客户端处理。80、320 和 20 ms 表示配置的仿真时间，不能与这个主机耗时直接相加，或据此断言系统已达到实时运行。

**用 RTC 衔接动作块。** Real-Time Chunking（RTC）可以配合异步推理：执行当前动作块时提前预测下一块，把预计来不及更改的前缀作为约束，并让可调整的后续动作平滑衔接。这样可以减少“执行完再等待新推理”的空档，但推理仍需耗时；缓冲不足、网络抖动或超时仍要处理。对本课的高层请求，还必须保留踢球触发与技能状态的保护，不能简单平滑所有数值。

[NVIDIA GR00T 部署指南](https://github.com/NVIDIA/Isaac-GR00T/blob/main/getting_started/real_world_deployment.md)与 [LeRobot RTC 说明](https://huggingface.co/docs/lerobot/rtc)介绍了这一思路。它是本课程的拓展设计：当前录像来自同步评估，尚未接入 RTC；采用 RTC 需要适配模型接口、动作块长度和异步执行器，再验证动作连续性与超时行为。

{#deployment}
## 真机上：在工作站推理，通过网络连接机器人

Microduck 的主控板不适合运行 GR00T 这样约 30 亿参数的模型。真机部署时，可以让机器人把图像与状态发给带 GPU 的工作站，工作站运行 GR00T，再把请求传回机器人；行走策略这样的小网络留在机器人本地持续运行。网络传输、图像编码和模型计算都计入端到端延迟；遇到超时或断网，机器人应进入受控停止或稳定站立，不能继续执行过期的前进请求。

::::{quiz}
GR00T 输出的前进请求是 0.3，能说机器人正以 0.3 m/s 前进吗？

:::{answer}
不能。前进请求是写入行走策略的原生指令值，实际速度取决于步态、地面和身体状态，需要从测得的运动中读取。
:::
::::
