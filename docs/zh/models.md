# 6.1 让智能体来帮忙

:::{lesson-intro}
:meta: 第 6.1 节 · 从课程走向自己的机器人任务

课程已经展示了从机器人模型、基础运动、感知到自主射门的完整思路。接下来，您可以把自己的机器人和任务交给熟悉的智能体，让它协助设计、实现和验证；您负责提供目标与约束，并根据实际证据判断是否达到了预期。
:::

{#start}
## 带上这份任务指南

仓库中唯一的英文任务指南 [ROBOT_TASK_GUIDE.en.md](https://github.com/NV-DLI/Microduck-Workshop/blob/main/ROBOT_TASK_GUIDE.en.md)把本课程的设计流程和实践经验整理成了可直接交给智能体的项目指南。它不依赖某一种智能体，也不要求照搬射门任务。Microduck 可以复用课程中的模型与技能；换成其他机器人时，需要重新确认关节、动作接口和物理参数。

将英文指南与项目文件一起提供给您的智能体，您仍可以用中文描述任务。请它先检查模型和传感器，询问缺少的必要信息，再推荐适合的模型、是否需要训练以及数据采集方案，最后提出分阶段实现计划。指南不是必须命名为 AGENTS.md 才能使用；如果您的工具按这个约定读取项目说明，也可以把适用的内容合并到自己的 AGENTS.md 中。

{#brief}
## 先提供这些信息

| 信息 | 应该说明什么 | Microduck 射门中的例子 |
|---|---|---|
| 机器人模型 | USD、URDF 或 MJCF，网格、单位、关节名称与顺序、限位、默认姿态 | 14 个受控关节，固定的默认站姿与动作映射 |
| 仿真环境 | Isaac Sim / Isaac Lab 版本、物理后端、地面、障碍与接触参数 | Newton、平地球场、球和球门 |
| 任务与成功条件 | 起点、目标、允许的动作、完成条件、超时与失败定义 | 接近足球、真实触球、整球过门并恢复站立 |
| 可用观察 | 相机、ToF、IMU、关节状态，各自的频率、坐标系和延迟 | 用视觉估计目标，用身体反馈保持运动稳定 |
| 已有能力 | 可复用模型、输入输出约定、数据与可运行入口 | 行走、踢球、站立恢复技能 |
| 运行资源 | 设备、显存、可接受耗时、训练预算与输出位置 | 先小规模验证，模型和日志写入新目录 |

缺少的信息可以明确写“尚不确定，请先检查或给出测量方法”。不要让智能体猜关节顺序、单位或成功标准；这些错误即使程序能运行，也可能使结果没有意义。

指南会引导智能体区分“机器人实际有哪些传感器”与“任务需要哪些信息”：哪些输入可以直接读取，哪些需要估计，哪些目前缺失。它应结合现有技能、运行资源与数据条件，说明适合复用规则或现成模型，还是需要训练感知模型、强化学习策略或 VLA；若需要训练，再明确数据从哪里来、如何采集与标注、怎样划分训练和独立验证。

{#workflow}
## 按能验证的小步骤推进

```{learning-flow}
label: 用课程经验组织自己的机器人项目
nodes:
- [核对模型与接口, 关节、坐标系、观察和动作]
- [建立最小闭环, 稳定初始化、站立与单个动作]
- [逐层完成任务, 感知、接近、执行与恢复]
- [独立验证与交付, 新条件、失败记录和复现方法]
details:
- 让智能体先读取真实模型和配置，把输入输出约定写成表格。能加载模型不代表关节与物理已经正确。
- 先在简单环境验证站立、行走或基础操作，检查目标与实际反馈。初始化辅助必须在执行策略前解除，不能把辅助支撑算作策略能力。
- 把任务拆成可单独检查的环节，先复用已有技能和简单控制，再根据失败证据决定是否需要训练感知、运动策略或 VLA。
- 冻结候选配置，用预先选定的新起点做测试，保留全部尝试；交付配置、模型来源、结果、局限与复现步骤。
layout: learning
```

Microduck 射门的经验是：先判断问题出在哪一层，再决定改什么。球估计错了，就检查传感器、坐标与时序；能看见球却走偏，就检查请求、反馈和制动；站位正确却踢空，就检查触球几何与技能交接。损失下降、视频流畅或一次成功，都不能替代任务验收。

{#handoff}
## 给智能体一个明确的起点

可以这样描述自己的任务，再附上模型、场景和指南：

> 请依据 ROBOT_TASK_GUIDE.en.md 帮我实现一个仿真机器人任务。机器人与模型路径是【填写】，仿真版本和物理后端是【填写】，可用传感器与现有策略是【填写】。我希望它在【场景和起点范围】完成【任务】，成功必须满足【可测量条件】，失败包括【填写】。可用资源和预算是【填写】。请先检查文件和接口，询问实际可用与任务所需的传感器输入，并推荐模型、是否需要训练及数据采集方案，说明理由和待确认事项；然后从最小可验证闭环开始，每阶段提供实际运行证据，保留失败和原始模型，再推进下一阶段。

每次继续工作时，让智能体先读取上次留下的配置、结果和待解决问题。这样它可以从已有证据接着做，您也能随时看清已经验证了什么、还缺哪一步。

在**容器内**运行下面的命令，核对固定模型的文件大小与哈希。

```{code-block} bash
:caption: Terminal · 容器内
:class: terminal

python3 scripts/run.py verify-models
```

这些文件随 Git 仓库一同提供，克隆仓库即可使用，无需 Git LFS 或额外的模型账户。`models/manifest.json` 记录了文件大小、来源和 SHA-256；实验入口在运行前会核对模型身份，避免误用同名文件。当前默认检测器的相对路径与 SHA-256 记录在 `models/scene-detector/deployment.json`。

**仓库自带。** 第 2–4 部分实验所用的权重；3.3 节预先训练好的 PPO 行走结果与 3.4 节的坡地训练日志在 `datasets/walking-ppo` 和 `datasets/terrain-ppo`（容器内 `/workspace/Microduck-Workshop/datasets/`，只读）。

**GR00T。** 5.2 节介绍的 GR00T 示范数据与检查点由课程方单独保存，学习本课程不需要下载。

## 练习数据与自己的输出

`datasets/scene-sample/` 是一套小型图像与标签样例，本课的动手实验不直接使用；它的规模不足以检验模型在真实环境中的泛化能力。自行训练的模型和日志请保存在 `outputs/`，`models/` 中的课程文件保持原样。
